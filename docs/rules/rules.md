# Project rules

> Mirror of `/mnt/project-files/plan/rules.md` (the source, owned by the "Decide strict project rules" thread). Synced by PR when it changes.

**Status: APPROVED by Malaka (2026-10-31).** These rules apply to every session in the project.

A copy lives in the repo at `docs/rules/rules.md` (CLAUDE.md points to it); the rules thread syncs it by PR whenever this file changes. Owned by the thread "Decide strict project rules" (the judge). Every session reads this file before starting work and passes the relevant rules into any subagent or executor prompt. To propose a change, message the rules thread; do not edit this file yourself.

## How the categories work

- **Strict (S):** only Malaka can change, pause or make an exception to these. No session breaks them, for any reason. If a task seems to need a break, stop and ask Malaka.
- **Necessary (N):** follow by default. A session may break one only when following it would clearly hurt the work, and it must (1) tell Malaka in its reply what it broke and why, and (2) report the break to the rules thread, which logs it in the Breaks log below.
- **Other (O):** conventions and current decisions. Follow them; change them when there is a good reason and say so in the reply.

## Strict

- **S1. No site code until Malaka says go.** "Continue" or "ok" is not a go. Applies to the rebuild branch, scaffolding and drafts in project files. (2026-10-30)
- **S2. Never commit secrets.** API keys and tokens never go in the repo, project files, memory or messages. Reference them as `${ENV_VAR}`; Malaka sets them in the cloud environment. (2026-10-30)
- **S3. Always commit tooling.** Every skill, plugin or MCP server added or fixed for the project is committed to the repo (`.claude/`, `.mcp.json`), pushed, and opened as a PR to main without asking first. Malaka merges it (S14). (2026-10-30)
- **S4. Keep MCP API calls to a minimum.** Use an MCP call only when needed; check repo skills, `components.js/` and earlier lookups first. context7: reuse known library IDs, one focused query. 21st Magic: one search, then `get_component` only for the result you use. Never poll or retry in loops; on a quota error stop and tell Malaka. Pass this rule to every subagent. (2026-10-31)
- **S5. Planner + executor for coding.** When coding starts, only the planner talks to Malaka. The executor talks only to the planner, in compact shorthand, with 1-2 line reports. (2026-10-30)
- **S6. Malaka's decisions stand until Malaka changes them.** Current ones: React + Vite with full prerendered HTML on every page in EN and IT (so AI crawlers can read it, 2026-10-31), palette = brown + gold base with deep forest green and brick red, tokens in `/mnt/project-files/plan/phase4/palette/palette.md` (2026-11-01), Tailwind CSS v4 with design tokens as CSS variables (2026-11-01), shadcn/ui as a toolbox only (2026-11-01), Motion (motion.dev) for every animation effect including hover and click, with GSAP only as a fallback for the pinned "two sides" moment (2026-11-01), static, prerendered site on GitHub Pages with no backend at launch; right after launch (Release 2, once secured and tested) a small serverless backend (decided 2026-11-01) that holds the AI API key, runs an AI site assistant (answers questions about Malaka and navigates the site; off-topic questions get a preset decline with no AI call), counts visitors first-party, and serves a login-protected admin page for adding projects and viewing stats; the AI is a paid service Malaka chose (S13): Anthropic Claude Haiku 5.5, spending cap 5 EUR/month (prepaid, auto-reload off), backend on Cloudflare Workers free plan (all 2026-11-01); launch services approved under S13/S18: Web3Forms (contact form), GoatCounter (cookieless visitor counter script), Namecheap email forwarding (2026-11-01); full plan: https://claude.ai/artifact/PedoQ5EZohfcyFiLoGGZH2, new site built on a fresh branch of the old repo and swapped in as main later, domain malakagonawala.dev. A session may suggest a change but never act on it alone. (2026-10-30/31)
- **S7. Never replace or force-push main, delete branches, or create repos without Malaka's OK.** The live site must keep running until the swap. (2026-10-30)
- **S8. Checklist items are never deleted or reordered without Malaka's OK.** (2026-10-31)
- **S9. Never invent content or proof.** Any copy Malaka writes or approves is used word for word. No made-up testimonials, stats, clients, emails or project details; any placeholder is clearly marked and flagged to Malaka before launch. (The old About Me copy was scrapped by Malaka on 2026-10-31; new About copy is written from the Phase 2 answers.) (2026-10-30, reworded 2026-10-31)
- **S10. Report honestly.** Say plainly when a check fails, a step was skipped, or something didn't connect. (2026-10-30)
- **S11. Nothing leaves the project without Malaka's OK.** No emails, calendar invites, Drive shares, or GitHub comments on other repos. (2026-10-31)
- **S12. Never delete files without Malaka's OK,** in project files or the repo. Moving something to an archive is fine. (2026-10-31)
- **S13. No new paid or metered service without Malaka's OK,** and no new API key requirement. (2026-10-31)
- **S14. Only Malaka merges PRs.** Sessions open PRs; they never merge them. (2026-10-31)
- **S15. Pick the executor model by task tier.** Sort each coding task by risk and how hard it is to check, not by file type:
  - *Light, Haiku 5.5, low effort:* text and headings, renames, links, alt text, single values (a colour or spacing token). No logic changes, 1-2 files, easy to check by eye.
  - *Medium, Sonnet 5.5, medium effort:* styling or layout inside one section, responsive fixes, a new static component from an existing pattern, adding a React Bits component, tests for existing code.
  - *Heavy, Opus 5.5, high effort:* new features and logic, state, interactions and UX flows, GSAP animation, build and deploy setup, changes across many files, bugs with an unknown cause, accessibility and performance passes.
  - Planning, design decisions and reviewing executor work stay on Opus (the planner). The hardest part of a task sets its tier; when unsure, go one tier up. If a model fails once, move the task up a tier instead of retrying on the same model. Batch small light tasks into one Haiku run. Max effort only when Malaka asks. (2026-10-31)
- **S16. Conversations with Malaka run on Opus 5.5 at medium effort.** Any thread or session that talks to Malaka uses Opus 5.5 with medium effort. (2026-10-31)
- **S17. Be as token-efficient as possible.** Read only what the task needs (graphify query, line ranges, not whole files or folders); don't re-read what is already known; no subagents unless needed; short replies and short thread-to-thread messages; batch small tasks; reuse earlier results instead of repeating searches or lookups. Never at the cost of correctness or S10 (honest reports). (2026-10-31)
- **S18. No trackers or third-party scripts** (analytics, chat widgets, ads) without Malaka's OK. (2026-10-31)
- **S19. Malaka's personal details stay private.** Phone, address, personal email and other private details never go on the site without Malaka's OK. (2026-10-31)
- **S20. Licensed assets only.** Fonts, images, icons and components are used only when their licence allows it; note the source. (2026-10-31)
- **S21. Preview before every task.** Before starting a task, show Malaka a preview of today's version next to the expected outcome, and wait for the pick before building. For visual work, use a labelled comparison grid like `plan/examples/preview-grid-example.png` (repo copy: `docs/rules/preview-grid-example.png`): a "TODAY" column, then numbered options (L1, L2, ...) each with a one-line label, one marked [REC]; rows for phone 390 dark, phone 390 light and desktop 1280; a title line saying what changes and what stays untouched. For non-visual tasks (config, tooling, content files), a short before/after summary instead. (2026-10-31)
- **S22. Every decision comes with a recommendation.** Whenever a session asks Malaka to choose (a question, a decision card, a preview grid), it includes one recommended option, clearly marked (e.g. [REC]), with a one-line reason. (2026-10-31)
- **S23. The checklist thread only keeps the checklist.** When Malaka pastes a checklist task into "Plan the portfolio project phases", that thread asks the coordinator for a new thread to do it. Several tasks pasted together go to one new thread, which does them one by one. The worker thread reports back to the checklist thread (N4). (2026-10-31)
- **S24. Checklist and rules links with every output.** Any reply that delivers an output or result to Malaka also attaches `/mnt/project-files/plan/checklist.md` and `/mnt/project-files/plan/rules.md` as outputs, so both are one tap away. (2026-10-31)
- **S25. No more code than necessary.** When two solutions do the same job equally well, always pick the shorter one (e.g. 50 lines over 200). No unused code, speculative features or needless abstractions. Shorter never means dropping correctness, accessibility (N14) or readability. (2026-11-01)

## Necessary

- **N1. Ask before pushing or opening a PR** for anything not covered by S3 or by a task Malaka asked for in that thread. (2026-10-30)
- **N2. The checklist thread owns `/mnt/project-files/plan/checklist.md`.** Other threads report done/undone work to "Plan the portfolio project phases" instead of editing the file. Small self-ticks are OK only if that thread is gone. Don't resolve the checklist thread. (2026-10-31)
- **N3. Checklist edit format.** Flip `[ ]`/`[x]` on that line only, add the date (and PR number if any), re-read the file right before editing. Items Malaka hasn't asked for are marked *(optional)*. A phase is finished only when its "Done when" line is met. Every item has a fixed id `phase.item` (e.g. 1.3); ids never change, and new items always go at the end of their phase. When Malaka says "fix 1.3", it means that checklist item. (2026-10-31)
- **N4. Report checklist changes live.** As soon as a thread finishes or undoes anything checklist-relevant (a merged PR, a decision by Malaka, a finished task), it sends one line to the checklist thread right away, not only at the end. Before a thread resolves, it also sends what it did and what's left. (2026-10-31)
- **N5. The diary thread owns the diary.** On "update diary", it first asks the checklist thread for that day's ticks and decisions, then writes the entry (date with correct weekday, Project, Summary, one bullet per category with comma-separated items, Open items), rebuilds `diary.pdf`, attaches it, and syncs `docs/diary/` via a PR. It tells the checklist thread anything it marks done. (2026-10-30/31)
- **N6. Diary only on request, one day per entry.** Update only when Malaka says "update diary"; an entry lists only work done on that date. Front pages (goal, stack, repo, tools, rules) are refreshed when those change. (2026-10-31)
- **N7. This rules thread owns `rules.md`.** Other threads report rule questions and Necessary-rule breaks here. (2026-10-31)
- **N8. Work through GitHub from the cloud,** not Malaka's local PC folder. (2026-10-30)
- **N9. Use only the approved palette.** Colours come from the tokens in `/mnt/project-files/plan/phase4/palette/palette.md` (brown + gold base, forest green, brick red; approved 2026-11-01). Ask Malaka before adding or changing a colour. (2026-10-30, updated 2026-11-01)
- **N10. The rebuild branch carries `.claude/` and `.mcp.json`,** so cloud sessions keep their skills and MCP servers. (2026-10-30)
- **N11. Follow the repo's CLAUDE.md for graphify:** `graphify query` before the first grep or file read on a code question; `graphify update .` after changing code. (2026-10-30)
- **N12. Save lasting facts to project memory in the turn they are learned,** one file per subject, keeping every other line when editing `MEMORY.md`. (2026-10-30)
- **N13. Check before every code PR.** Build, lint and tests pass; visual changes get phone and desktop screenshots in the PR. (2026-10-31)
- **N14. Accessibility baseline.** Semantic HTML, alt text, keyboard focus, AA contrast and prefers-reduced-motion support in every component. (2026-10-31)
- **N15. Performance budget.** Optimised images, only the font weights used, Lighthouse 90+ before merge. (2026-10-31)
- **N16. No new npm package without a one-line reason** in the PR; prefer what's already installed. (2026-10-31)
